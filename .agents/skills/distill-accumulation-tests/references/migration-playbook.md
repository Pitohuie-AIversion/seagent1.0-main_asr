## 1. 蒸馏目标

累计测试集通常混合了真实需求、历史缺陷、临时兼容、运行环境和人工回复示例。迁移目标不是逐行翻译旧 runner，而是形成三层资产：

1. **产品不变量**：必须长期保持的行为，如硬约束不可绕过、取消后槽位清空、重复发布无副作用。
2. **系统适配器**：目标版本的端点、请求字段、会话 API、状态注入 API 和产物读取方式。
3. **版本 Fixture 包**：设备、区域、时间、枚举、合法/非法组合和音频样本。

只有第一层应跨代稳定。第二、三层允许随架构和配置变化。

## 2. 测试形成模型

将每个新增缺陷或需求按以下闭环固化：

```text
需求/线上缺陷
  -> 最小可复现场景
  -> 明确前置 phase 与输入事件
  -> 构造单一异常轴 Fixture
  -> 定义结构化结果与禁止副作用
  -> 加入定向回归
  -> 加入累计集成集
  -> 配置漂移元测试
  -> 人工文档同步
```

场景至少回答：输入从哪里进入、旧状态是什么、发生什么事件、状态如何转移、哪些数据可以变化、哪些数据绝不能变化、失败时留下什么证据。

## 3. 可迁移用例契约

每个用例维护以下字段：

| 字段 | 含义 |
|---|---|
| `id` | 稳定编号，不因文件或框架变化而修改 |
| `title` | 可读场景名称 |
| `portable_invariant` | 与旧实体、端点和措辞无关的验收语句 |
| `layers` | 覆盖层，可多选 |
| `outcome` | 允许、软警告、硬阻断、收集、发布等结果类别 |
| `oracle` | structured、artifact、state-transition 或 semantic-fallback |
| `legacy_dependencies` | 仅用于找到旧配置，不进入新核心 |
| `next_gen_status` | planned、adapted、verified 或 deferred |
| `defer_reason` | deferred 时必填 |

多轮用例再维护：前置 phase、每轮输入或外部动作、每轮期望 phase、槽位增量、允许副作用和禁止副作用。

## 4. 断言强度

按下列顺序选择 oracle：

1. **产物级**：schema 合法、ID 一致、task/history 对应、文件集合和内容未被意外改写。
2. **结构化响应级**：约束 code/severity、phase、route、normalized slots、missing、done。
3. **状态转移级**：blocked_hard 保持、blocked_soft 被确认后进入待发布、取消回到 idle。
4. **语义回退级**：只在接口没有结构字段时检查少量稳定语义词。

禁止用以下方式制造“通过”：

- `lambda: True` 跳过关键轮次；
- 多个宽泛关键词用 `or` 拼成几乎必过的断言；
- 仅断言回复非空；
- 只看到“发布成功”文本而不检查 `done` 和产物；
- 将未修复用例永久标成 expected failure；
- 忽略 unexpected pass；
- 把测试专用分支写入业务代码。

若暂时只能用语义回退，目录中将 `oracle` 标成 `semantic-fallback`，并登记需要新增的结构字段。

## 5. Fixture 与隔离

### 5.1 权威来源

- schema 决定字段和枚举是否合法；
- runtime config 决定设备、区域、能力和状态引用；
- runner 决定实际执行行为；
- 人工文档只辅助复现和评审。

### 5.2 基线设计

- 建立一个“无告警正常基线”。
- 每个单约束用例只覆盖一个字段。
- 组合约束用例显式列出组合目的。
- 安全位置、禁入位置、不同海床等数据由配置推导，并用元测试验证。
- 设备面向调度的 ID 与遥测状态引用分开建模，不根据字符串猜测。
- fresh/stale 时间均由模拟时钟计算。

### 5.3 清理

- 每例使用不可碰撞 session ID；
- setup 失败立即失败，不进入对话；
- finally 中清理会话；
- 修改文件前保存原始字节，退出时通过临时文件和原子替换恢复；
- 真实发布写入隔离的临时目录；
- 并发测试使用独立进程和显式锁验证，不共享隐含全局状态。

## 6. 迁移批次

建议按风险与依赖排序：

1. **输入与路由**：普通对话、域内/域外、知识问答、ASR 转写入口。
2. **提取与 Slot**：完整首轮、稀疏补齐、单位规范化、口语、修改、无效候选不覆盖有效值。
3. **状态机**：确认、拒绝、取消、重复确认、重新检查。
4. **安全约束**：硬/软分级、组合约束、硬约束不可忽略、硬解除后软约束继续出现。
5. **发布与恢复**：TaskIntent schema、history、原子发布、重复发布、staging/final/quarantine 恢复。
6. **并发与真实链路**：跨进程锁、并发发布、真实 ASR 标注样本、前后端普通对话回归。

每个批次先适配少量代表用例，再批量迁移同构场景。不要在 P0/P1 未关闭时扩展低优先级场景。

## 7. 验证与证据

验证分四层：

1. 静态目录审计：ID 唯一、runner/manual/catalog 集合一致。
2. Fixture 与 verifier 单元测试：合法基线、非法基线、正反样本、清理异常路径。
3. 定向集成：只跑本批次 ID，保存逐步响应和失败详情。
4. 完整回归：报告 passed、failed、xfail、xpass、skipped 和总数，退出码非零表示不可验收。

每次迁移批次使用 `assets/migration-evidence.template.md`。没有真实输出时只能写“未验证”。

## 8. 常见错误

- 把旧端口、固定日期和绝对结果目录当成产品契约；
- 复制回复全文，导致文案调整触发假回归；
- 反过来只查“拒绝”一词，漏掉错误约束 code；
- 使用旧配置里的安全坐标，实际已落入新禁区；
- setup action 返回失败但 runner 继续执行；
- callable 动作不占 step index，verification 却按原列表下标错位；
- 首轮漏提后第二轮补齐，却宣称首轮提取通过；
- 只检查新增产物存在，不检查重复确认是否改写旧产物；
- 测试结束后遗留 telemetry、锁文件、session 或任务文件；
- 用模型成功加载代替真实 ASR 准确率测试。
