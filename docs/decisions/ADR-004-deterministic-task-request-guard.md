# ADR-004：确定性多任务守卫与枚举补提取

日期：2026-07-29
状态：已实现并验证

## 理解摘要

- TS-18 必须明确拒绝域外子任务，并要求用户选择一个域内任务。
- TS-19 不得擅自从多个域内任务中选择一个继续收集。
- 多任务阻断必须发生在任何 Slot 写入、phase 转移或 extractor 调用之前。
- TS-28 中明确出现的 schema 枚举值不得因 LLM 偶发漏取而丢失。
- 普通对话、QUERY、ASR、单任务创建、任务类型修改和发布接口保持不变。
- 修复不得绕过 SlotStore 事务、冲突处理、规范化或约束验证。

## 假设与非功能要求

- 单轮消息和任务别名集合规模较小，线性扫描满足性能要求。
- 不增加第三方依赖、缓存或外部服务。
- 不记录额外敏感内容，不向用户暴露模型或提示词信息。
- 守卫为纯业务分析，维护者通过确定性单元测试扩展任务别名和连接词。
- 枚举补提取只使用当前 schema 的 `allowed_values`。

## 方案比较

### 方案一：前置守卫与枚举补提取（采用）

新增纯业务任务请求守卫。`DialogueManager` 在 WRITE 路由之后、Slot
快照之前调用守卫。提取器在 LLM 结果之后补充原文中的唯一明确枚举值。

优点：确定性、修改范围小、不改变路由公共协议、复用现有事务和校验。

### 方案二：扩展 IntentRouter 协议

增加 `detected_tasks`、`unsupported_clauses` 等结构化字段。

优点：协议表达完整。缺点：影响路由器、Mock、调用方和测试矩阵，迁移范围较大。

### 方案三：仅修改 Prompt

强化多任务与字段提取提示。

优点：修改少。缺点：无法消除真实模型波动，不满足可靠性目标。

## 最终设计

### 多任务数据流

1. `DialogueManager` 先处理确认、取消等控制动作。
2. `IntentRouter` 完成 QUERY/WRITE 路由。
3. QUERY 保持现有只读链路。
4. WRITE 调用任务请求守卫。
5. 守卫使用知识库任务名称和别名识别不同规范任务类型，并按任务连接词分析子句。
6. 多个域内任务或域内/域外混合任务返回确定性选择提示。
7. 阻断路径只追加对话历史，不修改 SlotStore、phase、final result 或发布文件。
8. 单任务请求继续进入原有提取和原子事务流水线。

明确的“从 A 改为 B”“把 A 换成 B”属于任务类型修改，不按并发任务阻断。
同一规范任务的多个别名重复出现不算多任务。QUERY 类型的任务比较不进入守卫。

### 枚举补提取

`ParameterExtractor.extract_updates()` 完成 LLM 候选解析后，检查当前 schema
中带 `allowed_values` 的字段。若原文精确出现允许值且 LLM 没有返回该字段，
补充 `canonical_exact` 候选。同字段出现多个允许值时取文本中最后出现的值。

补充候选继续经过现有规范化、冲突检测、SlotStore 版本检查和约束验证，不直接写状态。
未知值不补充，已有 LLM 候选不重复。

## 测试与验收

- 纯守卫测试覆盖 TS-18、TS-19、同任务重复、任务替换、QUERY 比较和普通多字段输入。
- DialogueManager 测试验证阻断时 extractor 不调用且任务状态完全不变。
- 提取器测试覆盖明确枚举漏取补齐、未知值、多值最后优先和已有候选去重。
- 删除 TS-19 的 `expected_failure`；TS-18、TS-19、TS-28 均按普通严格测试运行。
- 依次执行定向测试、相关模块、离线全量、真实模型定向和完整累计集。
- 真实测试前后 `config/state.yaml` 必须字节一致，TS-27 发布产物必须通过 schema 校验。

## 决策记录

- 决定：多任务控制发生在 WRITE 路由后、Slot 写入前。
- 决定：不修改 `IntentRouteResult` 公共结构。
- 决定：混合输入同时说明域外部分不支持并要求选择一个域内任务。
- 决定：枚举补提取只能使用 schema 允许值，并复用现有验证流水线。
- 拒绝：仅通过 Prompt 调整解决真实模型波动。
- 拒绝：通过放宽测试断言或新增永久 XFAIL 接受间歇性回归。

## 实施结果

- 离线完整测试：`509/509` 通过。
- 本地 Qwen3.5-9B 真实模型累计集：TS-01 至 TS-39 `39/39` 通过，
  `0 expected failure`、`0 unexpected`。
- TS-18、TS-19、TS-28 均以普通严格测试通过；TS-19 未保留 XFAIL。
  TS-28 精确验证所有稳定规范字段，不再只验证字段无缺失和单个枚举值。
- 新增 TS-29 至 TS-39 均为普通严格测试。硬约束绕过在路由和抽取前确定性
  拒绝；忽略软警告与最终发布保持两个独立控制事件；取消任务清空未发布草稿。
- TS-34 验证动态更新 state 后“重新检查”会读取最新快照并解除已消失的硬阻断；
  TS-35 验证设备知识咨询不误入任务收集。测试动作回调的显式失败与异常均会使
  用例失败，避免环境更新未生效时产生假阳性。
- TS-36/TS-37 对明确标注的相对时间和 ISO 时间执行确定性候选恢复，并分别严格
  验证 C031 时间顺序硬阻断和 C030 过去时间软警告；模糊时间不做猜测。
- TS-38 严格验证 C007 硬阻断与未发布状态；TS-39 验证完成态重复确认在路由前
  幂等返回原 `intent_id`，且不新增或重写 TaskIntent。
- TS-27、TS-31、TS-39 的 TaskIntent 与 history 产物在隔离结果目录中通过 schema、
  `intent_id` 和最终历史状态一致性校验。
- 测试前后 `config/state.yaml` 的 SHA-256 均为
  `2f7c340868db240bb565e12326137278f23e5d100b7ade96e2d84a111e46627a`。
- 本轮未建立真实 ASR 准确率结论：仓库仍缺少带标注的领域音频夹具；这不影响
  文本进入 DialogueManager 后的 ASR 同链路回归结论。
